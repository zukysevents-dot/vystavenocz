## Kontext pro AI agenty

`AGENTS.md` je hlavní společný kontext pro Codex a ostatní AI coding agenty. `CLAUDE.md` je Claude Code vstup se stejnými závaznými pravidly pro práci.
Při každé smysluplné změně projektu aktualizuj **oba soubory**, aby se při přepínání mezi Codexem a Claude Code neztratil kontext.

**Growth V1 (doporučení a partneři):** `GrowthSettings.vue` v Nastavení firmy bezpečně vytváří referral kód, přijímá kód s idempotency hlavičkou a umožní partnerovi poslat žádost. Průvodce obsahuje laický návod `growth-referral-partner`; UI nesmí slibovat aktivaci tarifu, výplatu provize ani potvrzenou platbu. Kvalifikace nároku nastává až po důvěryhodném billing eventu na backendu. Kontrakt: `docs/backend/growth-referral-partner-v1.md`.

Za smysluplnou změnu se bere hlavně: architektura, doménový model, modulový systém, API kontrakty, deploy postup, bezpečnostní pravidla, workflow vývoje, testovací brány a důležitá produktová rozhodnutí.

**Rozsah MVP vs. placené moduly nad rámec — `docs/product/rozsah-mvp-vs-placene-moduly.md`.** Aplikace se vyvíjí na fixní cenu do dohodnutého termínu akceptace; všechno nad tento rozsah je samostatně objednávané a samostatně placené plnění. Než začneš stavět **nový modul nebo větší funkci**, zařaď ji: nový modul v `src/lib/modules.ts` nebo nová položka hlavní navigace, oborová vertikála, nová entita + migrace + nové API kontrakty, add-on z `src/lib/pricing.ts`, integrace na třetí stranu nebo požadavek, který přišel až v průběhu = **kandidát na plnění nad rámec**. V takovém případě **nezačínej stavět**, ozvi se písemně Patrikovi, vyžádej si písemnou objednávku od objednatele a zapiš položku do registru v tom dokumentu. Oprava chyby, dodělání jmenované funkce, refaktor, testy a dokumentace ke stávajícímu rozsahu jsou pořád MVP. Požadavek, který dorazí těsně před termínem akceptace, se řeší jako samostatná objednávka **až po akceptaci**, ne jako tichý přírůstek rozsahu.

Veřejný ceník (`src/lib/pricing.ts` + `IndustryPackages.vue`) prodává jen ověřené workflow, která v aplikaci už běží, a označuje je štítkem „V aplikaci". Nezaměňuj připravený integrační cíl za ostrý provoz: klientská zóna umí faktury a přijetí nabídek, ne online platbu bez runtime provideru; cashflow připraví e-mailovou upomínku, neposílá automatickou sekvenci; BankID a platební provideri zůstávají „Připraveno k napojení", dokud nejsou aktivní adaptéry a credentials.

Předávací protokol zakázky je neměnný snapshot práce a materiálu. API detail vrací `handover.items` s `kind` `work`/`material`; `useJobs` musí detail defensivně normalizovat, aby neúplná starší odpověď nikdy neshodila stránku zakázky.

## Co to je

Vystaveno.cz — fakturační + pokladní (POS) / gastro SaaS pro malé české firmy.
Tento repozitář = **frontend**: Vue 3 (`<script setup>` SFC) + Vite + TypeScript, package manager **npm**.
Migrace ze staré React appky (zazálohovaná ve větvi `legacy-react`, nevracet do working tree).

Produktová roadmapa modulárního Vystaveno + gastro priority je v `docs/product/modular-business-roadmap.md`. Kapitola **„Oborová funkční mapa a skladové doklady“** je závazný katalog oborových scénářů: `core + stock` je validní samostatný sklad bez POS/gastro a nové funkce nesmí míchat provozní skladové doklady s daňovými doklady. Při změně zásadního produktového směru ji aktualizuj společně s tímto kontextem.
Oborové akceptační scénáře a jejich pravdivý stav jsou v `docs/product/oborova-overovaci-pipeline.md`. Každý nový oborový claim musí projít řetězcem nastavení → běžný den → propojení → výjimka → dohledatelnost → laický návod. Frontend profil `warehouse` v `src/lib/modules.ts` je samostatný sklad (`core + stock`) bez POS/gastro; navigace a katalog mu nesmí nutit menu, alergeny, receptury, modifikátory ani prodejní cenu. Skladové doklady jsou v `SkladoveDokladyPage.vue` a přes `useInventory` mluví s `/stock-documents`; `Draft` nikdy nemění zásobu, až `Confirmed` ji smí změnit. `downloadStockDocumentPdf` stahuje autorizovaný `/stock-documents/{id}/pdf`; PDF je provozní snapshot dokladu, nikoli faktura, a koncept v něm musí zůstat viditelně označený. `EntityAttachmentsPanel` je znovupoužitelný i pro `stock-documents`: přílohy vedou výhradně na `/stock-documents/{id}/files`, nepřepisují doklad a nesmí se prezentovat jako fakturační vazba.
Uživatelská nápověda: `docs/product/vystaveno-user-guide.md` je centrální krátký průvodce všemi obory; `docs/product/gastro-user-manual.md`, `sluzby-zakazky-manual.md` a `opakovane-faktury-manual.md` jsou detailní návody pro konkrétní workflow. Při každé uživatelsky viditelné změně aktualizuj příslušný návod. V aplikaci je `/app/pruvodce`: z `src/lib/help.ts` zobrazí podle zapnutých modulů a role jen relevantní krátké postupy; drž ji v souladu s navigací a těmito návody. `docs/product/interni-test-manual.md` je stručný průvodce pro interní test na VPS staging (gastro start, sklad/inventura, uzávěrka, integrace, podpisy) s tabulkou „co je ostré vs. jen připraveno k napojení" — drž ji pravdivou.

`DodavatelePage.vue` a `useSuppliers` jsou adresář dodavatelů pod modulem `stock`; dodavatel není klient/odběratel. `Balení a ceny` používá `usePurchaseOrders` pro dodavatelský katalog SKU, velikost balení, minimum, cenu a dodací lhůtu. `NakupniObjednavkyPage.vue` a `usePurchaseOrders` vedou tok `/purchase-orders`: koncept → odeslání → volitelný e-mail → koncept příjemky se skutečně převzatým množstvím → samostatné potvrzení ve `SkladoveDokladyPage.vue` → záznam přijaté faktury. `Návrh podle skladu` je pouze předvyplnění položek pro vybraného dodavatele; používá minima/spotřebu backendu a zaokrouhlí minimum nahoru na balení, ale objednávku nikdy nevytváří ani neodesílá sám. Objednávka, e-mail, záznam faktury ani koncept příjemky nikdy nemění zásobu; až potvrzený doklad ji smí změnit a backend zároveň aktualizuje částečně/úplně přijaté množství. Přijatá faktura porovnává částku s potvrzenými příjemkami, ale není platba, účetní závazek, OCR ani DPH zaúčtování. Laický postup je v `docs/product/kompletni-uzivatelsky-manual.md` §10.2 a §12.

Import faktur z jiného účetního programu (`/app/import/faktury`, `src/import/invoices/`): jeden vstup přijímá **ISDOC/ISDOCX, Fakturoid XML, PDF i ZIP dávku** (včetně podsložek) — `loadInvoiceFiles()` formát detekuje sám, chyba jednoho souboru shodí jen ten řádek, ne celou dávku. **ISDOC je hlavní cesta „odkudkoli"** (`isdoc-invoices.ts`): český národní standard, umí ho Pohoda, Money, ABRA, Helios i iDoklad, data jsou strukturovaná a parser je tolerantní k namespace i verzi (5.x/6.x, s prefixem i bez); import je symetrický k našemu ISDOC exportu v `accounting-export.ts` a hlídá ho round-trip test. **PDF je až záložní cesta** (`pdf-invoice-fields.ts` + `pdf-invoices.ts`): pole se vytěžují z textové vrstvy, takže se **jednotlivé fakturované řádky NEROZPADÁVAJÍ** — vzniká souhrnná položka podle rekapitulace DPH, aby součty seděly na originál; co se nepodařilo přečíst, jde do `warnings` + `needsReview` a řádek se defaultně přeskočí (nikdy tichý dovoz). ## Dva repozitáře, jeden produkt

- **`vystavenocz`** (tento) — frontend (Vue).
- **`vystaveno-api`** (samostatný repozitář) — backend: .NET / ASP.NET Core + PostgreSQL + EF Core. Při vývoji leží vedle jako `../vystaveno-api`.

Frontend volá backend přes **same-origin `/api/v1`** (žádné CORS).
Datový kontrakt: `src/lib/types.ts` (FE) musí sedět s DTO na backendu; sdílené kontrakty jsou popsané v `docs/backend/*.md`.
**Když měníš tvar přenášených dat, uprav OBĚ strany** (FE typy + BE DTO) a případně kontrakt v `docs/backend/`.

## Deploy (produkce = VPS only)

Produkce běží na vlastním VPS (OVH), Docker stack: Caddy (TLS) → nginx (SPA statika + reverse-proxy `/api`) → .NET API → PostgreSQL.
Deploy soubory jsou v TOMTO repu (`Dockerfile`, `docker-compose*.yml`, `nginx.conf`, `Caddyfile`); API se builduje ze sousedního `../vystaveno-api` (musí ležet vedle).

Deploy je **pull-based** — po merge do `main` se samo NIC nenasadí. Uživatel to pouští ručně na VPS:

```bash
cd ~/vystavenocz && git pull
cd ~/vystaveno-api && git pull
sudo sysctl -w net.ipv6.conf.all.disable_ipv6=1   # VPS nemá IPv6, jinak build API padá na stahování
cd ~/vystavenocz && docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
sudo sysctl -w net.ipv6.conf.all.disable_ipv6=0
```

`Dockerfile` zapéká `ARG VITE_API_URL=/api/v1` do buildu → přebíjí `.env.production` (ten je pro VPS irelevantní, needituj ho kvůli produkci).
VPS `.env` musí obsahovat i `PAYMENTS_PORTAL_BASE_URL` (veřejná URL aplikace, typicky `https://$DOMAIN`), jinak online checkout faktury nemá kam vrátit zákazníka.

**PITR + hot standby (odolnost provozu, dávka 2):** PostgreSQL archivuje WAL (`archive_mode=on`, atomický `archive_command` přes `.tmp`+`mv`, `archive_timeout=300`) do povinného `WAL_ARCHIVE_DIR` z `.env` — bez něj produkční compose vědomě nenastartuje. Denní záloha kromě `pg_dump` pořizuje i fyzickou `basebackup.tar.gz`, zafixuje `PITR_TARGET_UTC`, zapíše hned za cíl prázdnou transakci (`pg_current_xact_id()` — bez ní se obnova na tiché databázi nemá o co zastavit a skončí `recovery ended before configured recovery target was reached`), vynutí `pg_switch_wal()` a počká na doarchivování; nedoarchivovaný WAL zálohu NEPUBLIKUJE. `ops/vps-verify-backup.sh` proto prokazuje obnovu na KONKRÉTNÍ ČAS (rozbalí base zálohu, přehraje WAL, povýší cluster na cíl z manifestu), ne jen na snapshot. Hot standby je za compose profilem `replica` (`ops/vps-replica-init.sh`, `VYSTAVENO_REPLICA_ENABLED=1`); failover je RUČNÍ promote podle postupu do 15 minut v `docs/vps-reliability.md`. Health hlásí selhávající archivaci, stáří fronty `pg_wal/archive_status/*.ready` (ne stáří poslední archivace — tichá databáze segment nepřepíná, takže starý test hlásil poplach každých 5 minut), velikost `pg_wal` (plný disk WAL zastaví databázi) a replikační zpoždění. Off-site mirror nese balíky, NE WAL archiv — při ztrátě celého VPS je RPO daný poslední zálohou; to řeší replika na druhém stroji.
